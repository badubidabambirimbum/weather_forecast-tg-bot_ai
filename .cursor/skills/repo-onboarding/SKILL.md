# Онбординг: анализ репозитория для нового агента

## Цель

За один проход собрать **проверяемый** контекст (по файлам и командам, не по догадкам) и выдать **бриф**, по которому другой агент может сразу править код, писать тесты и коммитить без повторного обзора.

## Быстрый старт

1. Прочитать `README.md` (оглавление → функциональности → структура → тесты → запуск).
2. Сверить дерево репозитория с разделом «Структура проекта» в README.
3. Просмотреть точки входа и критичные модули (см. [reference.md](reference.md)).
4. Проверить окружение: `.env.example` (не читать и не коммитить `.env`).
5. Зафиксировать правила: `.cursor/rules/*.mdc`, хуки `.cursor/hooks/`, skills `.cursor/skills/`.
6. Запустить `python -m pytest -q` (если среда доступна) и записать результат.
7. Сформировать отчёт по шаблону ниже.

## Workflow (чеклист)

Скопируй и отмечай по ходу:

```text
- [ ] git status / ветка / расхождение с origin
- [ ] README: назначение, компоненты, запуск, тесты
- [ ] backend/app.py — маршруты, auth, static
- [ ] backend/telegram_webapp.py + schemas.py
- [ ] backend/services/open_meteo.py
- [ ] bot/main.py + bot/forecast_args.py
- [ ] miniapp: index.html, app.js, logger.js
- [ ] tests/ — что покрыто
- [ ] .env.example — обязательные переменные
- [ ] .cursor/rules + hooks + skills
- [ ] pytest (или причина, почему не запускался)
```

## Что читать в первую очередь

| Приоритет | Путь | Зачем |
|-----------|------|--------|
| 1 | `README.md` | Источник истины по сценариям и командам |
| 2 | `backend/app.py` | API, session cookie, rate limit, static |
| 3 | `backend/telegram_webapp.py` | Валидация Telegram `initData` |
| 4 | `miniapp/app.js` | UX, session flow, forecast/geocode |
| 5 | `bot/main.py` | Команды бота, Menu Button, логирование |
| 6 | `tests/test_api.py` | Контракты API и auth |
| 7 | `.cursor/rules/*.mdc` | Язык, логи, git, production-quality |

Детальная карта файлов и потоков — в [reference.md](reference.md).

## Ограничения при анализе

- **Не** открывать, не цитировать и не коммитить `.env`, токены, `initData` целиком.
- **Не** полагаться на устаревшие планы в `.cursor/plans/` без сверки с `master` и README.
- При расхождении README и кода — **код и тесты** важнее; расхождение явно указать в брифе.
- Изменения в `backend/`, `bot/`, `miniapp/` могут требовать актуализации README (хук `git_policy.py`).

## Шаблон брифа (обязательный вывод)

Выдай отчёт **на русском** в таком виде:

```markdown
# Бриф репозитория: <имя проекта>

## Назначение
<1–3 предложения: что делает продукт для пользователя>

## Компоненты
| Компонент | Технология | Точка входа | Роль |
|-----------|------------|-------------|------|
| ... | ... | ... | ... |

## Критичные потоки
1. **Mini App + сессия**: ...
2. **Прогноз**: ...
3. **Бот /forecast**: ...

## API (кратко)
- `GET /health` — ...
- `POST /api/session` — ...
- (остальные защищённые маршруты — только с session cookie)

## Конфигурация
- Обязательные env: ...
- Локальный запуск: ...
- Telegram/ngrok: ...

## Тесты и качество
- Команда: `python -m pytest`
- Последний результат: N passed / не запускалось — причина
- Хуки: commit message conventional, запрет `.env` в staged, pytest перед push

## Правила проекта (Cursor)
- Язык ответов/комментариев: ...
- Логирование: `logging`, не логировать секреты
- Git: без force без запроса; коммиты только по просьбе пользователя
- Полезные skills: ...

## Риски и неочевидности
- ...

## Рекомендуемый следующий шаг
<одна конкретная задача, если пользователь её не задал>
```

## Эвристики для этого репозитория

- **Стек**: Python 3.10+, FastAPI, aiogram, vanilla JS Mini App, Open-Meteo.
- **Auth**: Mini App шлёт `initData` → `POST /api/session` → `HttpOnly` cookie `wf_session`; API без cookie → `401`.
- **Данные**: только Open-Meteo (геокодинг + прогноз); мок-endpoint удалён.
- **Деплой локально**: backend + ngrok/https + `MINIAPP_URL` + отдельный процесс бота.
- **Связанные skills**: `conda-python-env`, `readme-actualization`, `git-change-analysis-push`; субагент `git-change-push`.

## Когда остановиться

Анализ достаточен, если бриф закрывает вопросы: *где править фичу*, *как запустить*, *как проверить*, *что нельзя ломать (auth, cookie)*, *какие правила соблюдать*.

Если пользователь дал конкретную задачу — в конце брифа добавь раздел **«Задача и затронутые файлы»** со списком путей для правок.
